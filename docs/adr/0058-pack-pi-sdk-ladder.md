# The Pi SDK is resolved by a ladder, because a run has no node_modules

`pi-session.ts` loaded its SDK with the bare specifier `@earendil-works/pi-coding-agent`. A dev checkout resolves that; an Archon run does not. The run copies the pack into `artifacts/runs/<id>/workflow-source/`, which has no `node_modules` above it, so with `runner: pi` — the default — every startable Ticket failed at its first node. Measured on a live drain: `the pi runner could not start: Unexpected while resolving package '@earendil-works/pi-coding-agent' from .../workflow-source/global/workflows/ticket-dag/ticket-dag-drain/scripts/pi-session.ts`. Four rounds of smoke tests missed it because they ran from the repository, where `node_modules` exists.

`loadPiSdk` now walks an ordered ladder: `PI_SDK_PATH` (authoritative — when it is set it is the whole ladder, because a path that does not load is the problem to report, not a hint to ignore), then the bare name (the dev checkout, the one specifier only the import itself can settle), then the package directories this machine derives — the `pi` CLI from PATH, its symlinks followed, each `node_modules` above it checked for the package, and `process.execPath`'s `../lib/node_modules` — each kept only when the package is really installed there. A ladder that finds nothing throws `RunnerUnavailable` naming `PI_SDK_PATH` and the `npm root -g` fix, so the operator has one instruction and the failure stays a runner error rather than a Ticket's (ADR-0051).

`pi-sdk-repro.ts` copies the pack into a tree with no `node_modules` and drives the shape the run has: the bare name is unresolvable there, the ladder resolves and loads the SDK, and dropping the derived roots reproduces the live message verbatim. A live `runner: pi` drain over the same pack then implemented and merged a Ticket (`Status: MERGED`, `bun test` 2 pass), wrote its three-axis review and its summary.

Rejected: a vendored SDK in the pack (the pack ships no dependencies, and the SDK is versioned with the CLI the operator runs); requiring `PI_SDK_PATH` always (the dev checkout and every test would have to set it); `createRequire` from the pack folder (it resolves from the file's own location, which is the workspace copy that has nothing); spawning `pi` as a subprocess (the Pi adapter is an in-process SDK session by ADR-0033).

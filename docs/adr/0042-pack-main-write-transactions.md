# Only the caller opens a Main transaction; every writer asserts it is held

Main has one lock and one convention. `withMergeLock` is the only taker of the Target's `ticket-dag.lock` (inside its git dir), and it is re-entrant (a flag in `AsyncLocalStorage`), so the callers that own a transaction - `begin`, `settleAfterAgent`, `settleAfterConflict`, `pick`, `rematch` - wrap the whole sequence; every function that writes Main (`stamp`, `tryMerge`, `completeTicket`, `integrateCurrentMainIntoWorktree`, `ensureGitignoreLine`) calls `assertLockHeld` first and throws a named message when it is not. No writer takes the lock for itself: two conventions inside one module is how a torn sequence passes review, because re-entrancy makes nesting invisible.

Compound transitions have one owner. `main-writes.ts` owns `completeTicket` (assert, stamp MERGED, remove Worktree and branch - the idempotent complete of ADR-0029, called by settle and by rematch) and `integrateCurrentMainIntoWorktree` (assert, `rev-parse`, merge Main into the Worktree), while each caller keeps its own policy: settle stamps CONFLICT and keeps its failure message, begin stamps RUNNING and returns `resolve` on conflict. The step order inside the conflict route is pinned by a test instead of by statement order: after a conflict, the Worktree's own copy of the Ticket reads CONFLICT - which is only true if the CONFLICT stamp was committed to Main before Main was merged into the Worktree. Merging first leaves it reading MERGING, and `tests/settle-repro.ts` fails.

Rejected: self-locking writers (one invariant enforced two ways, with re-entrancy hiding the nesting); a lock token threaded through every signature (ceremony in a bun script with one process-wide lock); leaving the ordering rule to a doc-comment (it was: "Caller holds withMergeLock" was the only statement of it); a separate transaction object (the callers already are the transaction).
